The pitch

A quiet board for people you know.

Out of the box a strangers' key lands in a waiting room and learns nothing: no member list, no board names, no numbers. Growth is by invitation, and the invite tree is a feature. The sysop can switch registration to apply-and-approve or to open; invite-only stays the default.

01 Reach it with ssh

Members use the ssh they already have. No custom client, no browser, no account on a third-party service.

02 Alive, not a museum

Door games with shared worlds, chat with presence and whispers, polls, one-liners and a graffiti wall, with a sysop who has a voice.

03 Honest about privacy

The server can read nearly everything, and the product says so. Nothing the server can read is ever labelled “private”. The short version.

04 Yours to theme

Sysops change the name, art, menus, pages and style; members pick their own style and layout live. Security cues stay put, whatever the theme.

What is built

Features, by area.

Only what has merged to main is listed here. What is not built yet is marked, and the register is docs/features.md.

▸ Getting in

  • Waiting room for unknown keys, identical in every registration mode.
  • Registration modes invite (default), apply and open.
  • Invite codes: single use, expiring, bound to the inviter, with quotas and an invite tree.
  • Sysop queue to approve, deny or vouch.
  • Keys and passwords: password sign-in is on by default; keys are the extra. Link a new device with a code, or use a staff recovery code.
  • Founder claim: a one-time token printed on first start makes you sysop.

▸ Talking

  • Forums with search, and a full-screen editor with quoting and autosaved drafts.
  • Chat rooms with presence and whispers, and chat beside any screen (Ctrl-T).
  • Community: one-liners, a graffiti wall, last callers and polls.
  • Internal mail, encrypted at rest, with no staff reader.
  • RSS: feeds in as read-only boards (with an SSRF guard), and feeds out for public boards.

▸ Look and feel

  • Nine styles, seven layouts and 17 widgets, switched live.
  • Board art from CP437 .ans files, parsed safely into cells.
  • Mouse, a Ctrl-K command palette, toasts, a live header ticker.
  • Motion that turns off, and a plain ASCII tier with no icons.
  • Sysop menus and pages, theme packs you can import and export.

▸ Doors

  • Five original games on one door framework, each with full terminal screens.
  • Deterministic engines with replay tests and a seeded RNG.
  • Sandboxed by construction: a door has no filesystem or network handle to use.
  • Shared worlds and a nightly tick that catches up after downtime.

▸ Keeping it safe

  • One shared sanitizer for every piece of text that is not interface chrome.
  • Security cues that a theme cannot hide or restyle.
  • Roles and permissions, one named permission per action, plus an append-only audit log.
  • Rate limits per address and per key, and bounded sessions.

▸ Running it

  • One static binary and one data directory.
  • SQLite by default, or Postgres with TLS required, tested against the same suite.
  • TOML config with RUSSH_BBS_* overrides.
  • Clean shutdown that checkpoints the database.

▸ Not built yet planned

  • File areas over SFTP (M4): the blob store exists, the member-facing areas do not.
  • Sysop admin screens and an audit-log viewer (M5).
  • GraphQL API (M5), PGP mail (M6) and end-to-end encryption with a native client (M9).

Telnet access

Telnet, if you must, and labelled.

Telnet is off by default: out of the box nothing listens on it. A sysop who wants it turns on two separate switches, and the board then says LOW-SECURITY MODE in its log and on staff screens.

  • Connect with a plain telnet client; type new at login: to reach the same waiting room as over ssh.
  • The whole session crosses the network unencrypted, password included. Every telnet screen carries a fixed UNENCRYPTED marker on its last row that nothing can hide.
  • Staff powers are dropped over telnet: a sysop who signs in that way is an ordinary member for the session.
  • Prefer ssh. Never reuse a password you typed over telnet.

Run your own board

From a clone to a claimed board.

There are no published binaries and no published container image yet: the owner has not cut a release. Today you build from source. These commands were run from a clean data directory with a real OpenSSH 9.6 client.

  1. Build it

    $ git clone https://github.com/pdxgeek/russh-bbs && cd russh-bbs
$ cargo build --release -p russh-bbs-server
# about four minutes on a small machine; rust-toolchain.toml pins the toolchain

  2. Start it

    $ target/release/russh-bbs-server --listen 0.0.0.0:2222
# first start creates the host key, the database and mail.key in one data directory,
# logs the host key fingerprint, and prints a one-time setup token to the console

  3. Claim it

    $ ssh -p 2222 claim@your.host
# paste the token, choose a password: you are now founder, with the sysop role

    A restart before the claim prints a new token and voids the old one. Anyone who can read the console before you claim can claim the board, so do it first.

  4. Check it from outside

    $ ssh -p 2222 new@your.host
# what a stranger sees: the waiting room, and nothing else

Privacy, plainly

Who can read what.

  • The server, and so the person who runs it, can read nearly everything: posts, chat lines, whispers, profiles, who invited whom.
  • The exceptions are PGP-encrypted mail (you encrypt it yourself before you paste it in) and files you encrypt yourself before uploading (file areas are not built yet).
  • Internal mail is encrypted at rest and has no staff reader. That protects a stolen disk or database copy; it does not hide mail from whoever controls the running server.
  • ssh encrypts the wire, not the server. Telnet encrypts nothing. End-to-end encryption needs a native client that does not exist yet, and the board never fakes it: it will not call anything “private” that the server can read.

Architecture

Thin front ends, one core.

One Cargo workspace. Rules live in russh-bbs-core; the front ends stay thin and call it. A rule that exists in two front ends is a bug.

Front ends stay thin
The SSH server and the telnet listener drive the same screens. Neither decides who may do what; they ask core.
One core
Access, invites, mail, chat and the sanitizer live in russh-bbs-core. Core depends on nothing concrete.
Two databases, one test suite
SQLite is the default. Postgres has its own forward-only migrations and passes the same behaviour tests; there is no silent fallback from one to the other.
Doors depend on the framework only
A game is its own crate on the door framework: a deterministic engine, a saves host, a source audit that checks it reaches for no filesystem or network.
Dashed means not built
SFTP file areas and the GraphQL API are planned; their crates are reserved.
Roadmap

Where it is, and what is planned.

Each milestone ends with something runnable and with a QA pass by a session that did not write the code. Nothing past the current milestone is built, and there are no dates: the plan’s estimates are guesses. The full plan is docs/milestones.md.

  1. M0 – M3 merged

    Workspace and shared sanitizer; the SSH server and waiting room; invites, roles, profiles and the sysop queue; forums, chat, mail, feeds, telnet, passwords and the scheduler.

  2. M3.5 Look and feel merged

    The modern UI: styles, layouts, widgets, board art, sysop menus, mouse, effects and the command palette.

  3. M4 Files and doors in progress

    The door framework and the five games are in. File areas over SFTP, scanning and the global new-scan are still to do.

  4. M5 Sysop tooling and API planned

    An admin TUI, moderation workflow and audit-log viewer, notifications and digests, data export and deletion, an accessibility mode, backups with a tested restore for every backend, and a read-only GraphQL API. Then a closed beta.

  5. M6 External mail planned

    Inbound and relayed outbound mail, and PGP mail through local gpg.

  6. M7 Plugins planned

    A WASM plugin runtime for menu scripting and community doors.

  7. M8 Open edges planned

    Opt-in federation, an NNTP gateway, an IRCv3 gateway for chat rooms, finger and a directory listing.

  8. M9 Native client and E2EE planned

    A native client with end-to-end encrypted messages, multi-device, hardening and an external crypto review. Until then the server can read everything except what you encrypt yourself, and says so.
