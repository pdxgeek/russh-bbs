# M4-F2 walk: file areas over real `ssh` and `sftp`

Date: 2026-11-06. Branch `m4/sftp-file-areas`. **What was run:** the real server binary (`target/debug/russh-bbs-server`, SQLite, local blob directory, no scanner, a fresh board), claimed with OpenSSH 9.6 (`ssh claim@127.0.0.1`, the token from the console), three members seeded straight into the database (`ann`, `mo` the moderator, `bob`; the earlier QA walks did the same), then driven by [`m4-f2-screens/walk_files.py`](m4-f2-screens/walk_files.py) with the OpenSSH `ssh` (a pty under `pyte`) and `sftp -b` clients. Keys were generated by the script. The same scenario also ran as automated tests against MinIO (`crates/server/tests/sftp.rs`, see below).

## What happened

1. The founder opened **Files** (`a`), saw "There are no file areas you can see yet." and, with `n`, made the area *Manuals* ([01](m4-f2-screens/01-areas-empty-founder.png), [02 the form](m4-f2-screens/02-new-area-form.png), [03](m4-f2-screens/03-areas-with-manuals.png)).
2. `ann` uploaded `router-guide.txt` (1,000 bytes) and `network-diagram.bin` (700,000 random bytes) with `sftp put`. Her `ls -l /1-manuals/pending` listed both, with their real sizes.
3. `bob` listed `/1-manuals`: only the empty `pending` directory. `get /1-manuals/pending/1-router-guide.txt` answered `File ... not found.` and wrote nothing.
4. `mo` (moderator) opened Files, then the queue (`q`), the file's details and approved it; the second file was rejected after a confirmation ([04](m4-f2-screens/04-areas-moderator.png) to [09](m4-f2-screens/09-after-reject.png)).
5. `bob` listed the area again (the approved file, with `ann` as its owner), downloaded it with `sftp get`, and the SHA-256 of the download **equals** the upload. His TUI screens at 80x24 and 132x43 ([areas](m4-f2-screens/10-bob-areas-80x24.png), [area](m4-f2-screens/11-bob-area-80x24.png), [file with its sftp path](m4-f2-screens/12-bob-file-80x24.png), [download list](m4-f2-screens/13-bob-download-list-80x24.png); the 132x43 ones are beside them) show the path `/1-manuals/1-router-guide.txt` and the line "The board can read every file here".
6. The download list added in the TUI was served as `/downloads` (`get /downloads/1-router-guide.txt` worked), and `mkdir`, `rm`, `rename`, `ln -s`, `get /../../etc/passwd`, `get //etc/passwd` and `ls /9-nothing` were each refused (`Permission denied` or `not found`); nothing was written outside the work directory ([transcripts](m4-f2-screens/sftp-transcripts.txt)).

## Automated tests of the same story (not a walk)

- `crates/server/tests/sftp.rs`: the full scenario with OpenSSH `sftp` on the **local backend and MinIO** (bitnamilegacy/minio in `russh-bbs-minio-sftp`, port 19100) with one shared function; per-file and per-day limits; auto-approve; a restricted area answering like a missing one; traversal paths; refused operations; a 3 MiB file with a hash check and a resume (`reget`); the scanner against a fake `clamd` (infected: the transfer fails and nothing is stored; a scan error: the file waits; the scanner down: nothing auto-approves); SFTP off, a stranger's key and a suspended member refused; and the Files screens driven through a real `russh` client (browse, queue, approve, tag, search, download list).
- The store suite (`crates/store/src/suite/files.rs`, 13 checks) on SQLite, Postgres 16 and TLS-required Postgres 16.

## Not exercised

- **Telnet end to end.** The telnet note is a unit test of the screen (`FilesMode::Telnet`) and the mode is chosen from the transport; no telnet client was run against the Files screens.
- **A real ClamAV.** Only a fake `clamd` that speaks `INSTREAM`.
- **Another SFTP client** (WinSCP, FileZilla, `rsync` over SFTP). Clients that write out of order fail with "uploads must be written in order"; clients that set attributes after an upload fail the `setstat` (a client that does it on the open handle is told OK).
- **The server run against Postgres** with SFTP (the walk used SQLite; the store suite covers Postgres).
- **A multi-gigabyte file**, and a stalled client mid-upload (the dropped-handle case is a unit test of the queue).
- **Other terminals** than the pty under `pyte`.
