## Verdict

**M2 passes the gate.** The "Done when" line holds over a real OpenSSH client against the container image built from `main`, from an empty volume: a member (the founder) created an invite that a second key redeemed, and a stranger asked for an invite, was vouched for by a trusted member and approved from the sysop queue, then signed in. I found **no high finding**: nothing leaked to an unknown, pending or suspended key, no input reached the screen unsanitized, no secret or typed text reached the log or the audit table, the audit table refused UPDATE and DELETE, and a database made by an older `main` opened on current `main` with every row and id intact on SQLite and Postgres.

Two **medium** and a handful of **low** findings are below. Per the gate rules the next milestone should not start until the medium rows are Done or the owner accepts them; they do not block the "Done when" line.

### Break it

- **Control characters, ANSI, bidi, private-use:** typed through a real `ssh` into profile fields, the request handle and message, the invite code and the open-mode handle: `ESC[31m`, `ESC]0;...BEL`, `ESC[2J`, NUL, C1 `0x9b`, U+202E, U+2066, U+200B, U+E0B0, U+F06E, U+301A/U+301B, `◉`. Stored values contained none of them (`Alice` from `Al<U+202E>ice<ZWSP>`; `heer` from `he<ESC>[31mer<BEL>`; `about server   31m xy`). The sysop's view of a hostile request carried no ESC, no U+202E and no OSC (the visible leftover `0;pwn` is plain text). Non-ASCII handle letters are dropped as typed and the form echoes what was kept (`Jos<U+00E9><U+0430>b` showed `Josb`).
- **Oversized input:** a 5,000-character invite code and 600 characters in the request message: the message was capped at 280, the code gave the normal refusal. 3 MB pushed at the request form: `session is over its request budget; disconnecting ... dropped_input_bytes=1023340`; the server stayed up.
- **Flood:** 60 raw TCP connects from one address: 10 got an SSH banner, the rest were closed; the next legitimate connect worked after 4 s. CPU 0.00 %, memory 3.3 MiB afterwards.
- **Resize storm in the container (no tty):** 4,780 window-change requests in 12 s with sizes from 1x1 to 1000x1000 (`setwinsize`): the session stayed alive and responsive, container CPU 0.01 %, memory 12.4 MiB, no panic or error in the log. A 200x50 window centered the box.
- **Disconnect mid-screen:** the founder's `ssh` was SIGKILLed on the approve-confirm screen: the request stayed pending, no account was made.
- **Concurrent sessions:** covered in the limits row above.
- **Log check:** after all of this, `docker logs` held no invite code, no typed handle or message, no request text, no profile text. It holds the public key fingerprints and peer addresses by design (`docs/threat-model.md` "Logging"). The setup token is in the log until the container's logs are rotated, as `docs/deploy.md` documents. No `ERROR` line and no panic.

## Findings

### M1. MEDIUM: a `cosysop` can rewrite a `sysop`'s profile (no rank rule on profile edits)

Reproduction: `INSERT INTO access_grant (account_id, role, resource_kind, resource_id) VALUES (2,'cosysop','',0)`, then `ssh` as `alice`: `u`, `l`, open `founder`, `e`, typed `SYSOP-impersonated` and `hacked by alice`. The profile of the sysop was saved ("Profile saved."), and the audit table got `profile.edited | actor 2 | target 1 | fields display_name about`.

Why it matters: D60 (6) said the rank rule between editor and target would be applied once M2-B2 lands. M2-B2 landed, its note in `docs/coordination.md` says `Snapshot::top_rank()` exists, and `core::profiles::edit_grant` (`crates/core/src/profiles/service.rs:147`) still only asks for `members.edit`. Staff only, so no member can do it, but a lower-ranked staff account can rewrite the highest-ranked profile text that every member reads. The audit row proves who did it. Workaround: do not grant `cosysop`/`moderator` the permission until fixed. `docs/profiles.md` records the gap honestly. Fix: refuse when the target's top rank is not below the editor's, with a core test, then update `docs/profiles.md`.

The M2-B2 editing services themselves (`create_role`, `set_role_permissions`, `delete_role`, `grant_role`, `revoke_role`, `grant_permission`, `revoke_permission`) refuse rank escalation in the core tests I ran: `granting_a_role_follows_the_rank_rule_and_never_grants_waiting`, `changing_a_role_needs_rank_below_and_refuses_locked_roles`, `a_role_is_created_below_the_actors_rank_and_never_at_or_above`, `the_last_sysop_grant_cannot_be_revoked`, `every_service_is_refused_without_roles_edit_and_writes_nothing`, and `escalation_is_refused_on_the_real_role_data` on SQLite and on both Postgres runs. No screen calls them yet (M5), so they could not be reached through `ssh`.

### M2. MEDIUM: one unknown action name makes the whole audit log unreadable

`crates/store/src/audit_rows.rs:63` returns `StoreError::Corrupt("stored audit row has an unknown action")`, and `sqlite/audit.rs:81` (and the Postgres twin) `collect()`s the page into one `Result`, so one such row fails the page for everyone. The unit test `a_hand_written_audit_row_with_an_unknown_action_is_corrupt` pins that behaviour on purpose. It is latent: no screen reads the log until M5. After a downgrade to a binary that predates an action, or a renamed action, `audit.view` would fail for good, and the table cannot be repaired because it is append-only (triggers refuse UPDATE and DELETE). Fix before the M5 screen: read an unknown action as a labelled unknown entry (or skip it with a visible count), keep `Corrupt` for rows whose structure is invalid, and add the test on both backends. Note the same downgrade is already refused by the migrator (`a_database_from_a_newer_binary_is_refused`), which limits the exposure to renamed actions and to a sysop deleting migrations.

### Low findings

**L1. Postgres TLS tests share one database (confirmed).** The `tls::` tests in `crates/store/src/postgres/tests.rs` call `PostgresStore::open` on the database named in `RUSSH_BBS_TEST_POSTGRES_TLS_URL` (`.../postgres`), not a scratch one. I ran them on current `main` (migrates the `postgres` database to version 10) and then from the older checkout `c0539c9`: `Migrate(VersionMissing(7))` in `require_connects_over_tls_without_a_root_cert` and `verify_full_with_the_root_cert_connects_over_tls_and_migrates`. CI starts a fresh server per run, so only local reuse hits it. Fix: give those tests a scratch database like `PgHarness::fresh`.

**L2. `registration.capped` precedes the `account.created` it belongs to (confirmed).** In the audit table: id 26 `registration.capped | day 20759 cap 2`, id 27 `account.created | via open state active` (the account that took the last place). Both are in one transaction; only the order is odd, and a reader of the log sees the cap reached before the account exists. Fix: write the cap row after the account row.

**L3. A form left open across the cap (confirmed).** With `open_daily_cap=1`, a second visitor with the create-account form already open typed a handle after the first took the place: "That account could not be created. Try a different handle, or disconnect and connect again later." (identical to every other refusal, as designed). Esc returned to a waiting room that still said `[n] Create an account`; only a new connection showed the apply room and its notice. Already noted by M2-G; needs one method on `Screen`.

**L4. Session concurrency is per process.** `docs/access.md` documents it. I did not run two server processes on one database, so the claim that each process counts for itself is from the code and the docs, not from a run.

**L5. Stale status text.** `docs/features.md` line 3 says "M2 and later rows are Planned" while eight M2 rows are Implemented; `docs/README.md` says "M0 and M1 are merged (the M1 QA gate has not passed yet)". **L7. LOW (informational, no regression found): an unthrottled window-change burst is disconnected by design.** A loop that changed the window size about 1,500 times in 0.1 s (no pause) made the server drop the session: `session is over its request budget; disconnecting ... dropped_input_bytes=0` (three times: one `alice` session and two founder sessions). That is D49: 200 requests a second, a 400-request burst, and 1,000 strikes disconnect. The budget code in `ssh/` is unchanged since `00eba21` (only a comment differs), so this does not come from the fixes. The first report's "4,780 window-change requests in 12 s kept the session" is not reproducible at that rate here; what reaches the server depends on how `ssh` coalesces `SIGWINCH`, and one of my fast runs ended in a `pyte` parser error in my own client, not a server fault. A person dragging a window is nowhere near the limit (about 60 a second). If the owner wants "a resize storm never ends the session" as a rule, D49 would have to change; today the documented rule is "a storm past the budget ends the session". Nothing to fix unless the owner says so.
