# QA report: M3.5 Look and feel, phase 1 of 2

Reviewer: QA session (did not write the code; no product code changed, only this file, `docs/qa/m35-screens/` and rows in `docs/coordination.md`). Date: 2026-11-05.
Tested: `main` at **`46c6903`** (merge of PR #118). Merged and in scope: UI-1 frame (D109), UI-2 styles and layouts (D117), UI-3 board art (D123), UI-5 doors on full ratatui (D104), UI-8 effects and graphics (D124), UI-10 widgets (D122), FIX-UI-2a doors at full depth in a layout-sized box (D121). **Not merged, so not in this report:** UI-4 screens, UI-6 sysop menus, UI-7 theme gallery and packs (shared screenshot renderer, Blocks border set, Terminal.app hint), UI-9 mouse, palette and toasts. Those, and the "every screen on the new widgets" half of the brief, are for phase 2. The format follows [m3.md](m3.md).

## Verdict

**Phase 1 of 2: no high finding; three medium findings. The M3.5 gate is not closed.** The parts of the look-and-feel work that are merged hold the product rules that matter most:

- The reserved bold+reverse style appeared **only on the marker cell, at its chrome position, in all 2,205 style x layout combinations** I walked (every one of the 7 layouts x 9 styles, at 80x24 and 132x43, in the Nerd Font, Unicode and ASCII tiers, in colour and in mono, over ssh and over a raw telnet client, at truecolor, 256, 16 colours and vt100). The count is made on the raw byte stream, not only on the final screen.
- **1,564 screens of hostile data** (member names, board names, threads, posts, one-liners, wall, polls, feed board items, chat room name, hostile `.ans` and `.art.toml` files) showed no escape sequence, no reserved glyph or delimiter, no reverse cell off the marker and no text outside its box. Every screen was compared with the same screen of a length-matched benign board.
- Widgets leaked nothing: a member without a grant saw no word of a restricted board in any widget or screen (0 hits in 25 member runs; the same words are visible to the sysop as the positive control), the waiting room is byte-identical on three boards with different data, sysop locks beat what a member had stored earlier, and the refresh gap is 10 s.
- Effects: motion off is one static frame, any key ends the intro and is handled, the final intro frame equals the static screen cell for cell, no sixel, kitty or iTerm sequence anywhere.

The three **medium** findings, with FIX rows proposed in `docs/coordination.md`:

## Environment and recipe

Linux container, 4 cores, OpenSSH 9.6, `tmux 3.x`, Python 3.13 with `pyte` and `pillow`, no Docker (not needed: the server binary is the object under test). All clients ran **inside tmux panes**: OpenSSH (`ssh -tt`) and my own raw telnet client (`tools/telnetc.py`: answers NAWS and terminal type, no local echo, logs the raw wire). `tmux pipe-pane` copied every byte the client printed to a file, which was fed to `pyte` (cells, colours, attributes) and to a second `pyte` screen that records every cell **drawn or erased while reverse video was on** (`tools/lib.py`, class `Tally`): that is the raw-byte count for the reserved style. `pyte` has no alternate screen; the harness resets on `ESC[?1049h`. Screenshots are made from the `pyte` cells with `docs/qa/m4-s3-screens/render.py`.

```bash
git rev-parse --short origin/main                                 # 46c6903
SQLX_OFFLINE=true cargo build --release --locked -p russh-bbs-server   # about 7 min
# scratch boards, one per walk, each its own data directory, host key and ports (2322 to 3023), telnet on with password login:
tools/start.sh DATADIR PORT TELNETPORT [env...]  ;  python3 tools/claim.py PORT TOKEN
```

Keys and passwords were made at test time and are not in the repo. Two things I did by hand to the scratch databases and nothing else: (1) the `member` and `trusted` roles' `calls_per_day` and `minutes_per_day` limits were set to unlimited (a member gets 5 sign-ins a day and a walk makes hundreds; the same step the M3 reviewers took); (2) the hostile and benign boards were **seeded with SQL** by `tools/seed.py` (a typed keyboard cannot send ESC, C1 or non-ASCII, so the only way to put hostile text in every field is to store it and read it back through the screens, which is also what a legacy or imported row would be). Nothing was run under Docker, GitHub Actions was not started, and no `tc` qdisc could be used (see 4).

Two harness bugs of mine cost reruns and are worth knowing: the icon check is asked once per account, so my first "ASCII" and "Unicode" hostile runs were really Nerd Font (I set the tier explicitly through Terminal settings `i` and reran all of them); and the first door "256 colour" and "16 colour" runs still sent `COLORTERM=truecolor` because `ssh -o SetEnv` takes the first value (reran with the variable omitted). The numbers below are from the corrected runs.

## Findings

### M1. No marker, no status row on reader, mail, chat, members menu, door list and running doors (Medium)

D39 and the AGENTS.md rule: the `LOW-SECURITY` marker is drawn in the status row's left cell on **every screen of a staff session while the board is in low-security mode** (FIX-M3-6, folded into UI-1: "`LOW-SECURITY` on every staff screen, by the status bar"). The status bar is drawn only by screens that use `FrameSpec` (`classic.rs`, `forums/draw.rs`, `settings`, `members` list, the widgets screen and the art preview). The screens "not converted" in `ui.md` (reader, mail, chat, editor body) never drew one, and the door screens, which UI-5 and FIX-UI-2a describe as "the same box and status row as every other screen", do not either: the door box now runs to the last row.

Reproduce: start with `RUSSH_BBS_TELNET_ENABLED=true`, claim as the founder, sign in over `ssh` (any tier, 80x24 or 132x43, any layout), then press, from the main menu: `m` (mail), `m` `c` (compose), `c` (chat), `d` (door list), `d` `2` Enter (Saltmarch), `u` (members menu), and in `f` `1` `1` (a thread's reader). On each of them the last row is the box's bottom border (or blank); `pyte` shows **no reverse cell on the whole screen**. The same keys on a converted screen (`f`, `y`, `i`, `s`, `o`) show the marker at (last row, col 0).

Evidence: [data/scan-80-nerd.txt](m35-screens/data/scan-80-nerd.txt), [scan-132-ascii](m35-screens/data/scan-132-ascii.txt), [scan-80-unicode-focus](m35-screens/data/scan-80-unicode-focus.txt): `NO MARKER` on 11 of 39 steps in each tier and layout. Screenshots: [menu with the marker](m35-screens/f1-menu-marker-present.png), then without it: [Saltmarch](m35-screens/f1-door-saltmarch-no-marker.png), [door list](m35-screens/f1-doors-no-marker.png), [mail](m35-screens/f1-mail-no-marker.png), [chat](m35-screens/f1-chat-no-marker.png), [reader](m35-screens/f1-reader-no-marker.png).

Expected: the marker cell on every screen of a staff session in low-security mode, including these. Over telnet it holds (the transport's `UNENCRYPTED` footer is on all of them, 13 of 13 screens checked), and non-staff sessions are not marked by design (D93), so the exposure is **the staff on an ssh session, on exactly the board that has turned telnet on**. That is a real cue that is missing, but nothing hostile can draw it or hide it, so Medium and not High. The reader, mail and chat part is UI-4's job and may land in phase 2; the **door** part (UI-5, D121) is not, and the door screens are the ones that now hold the whole screen. Fix: FIX-M35-1.

### M2. The ASCII tier draws `█` and `║` when the menu scrolls (Medium)

`ui.md` (UI-1, UI-2): every style and layout draws only ASCII in the ASCII tier ("tests check every cell"), with a `#` scrollbar. The main menu's list scrollbar is the one thing that does not.

Reproduce: sign in, Terminal settings `i`, answer `n` then `n` (ASCII icons), Esc; use a window of 80x14 (or 40x12) and the classic layout (also lightbar, dashboard, wide, split): the right edge of the menu box shows a column of `█` (and `║` where the thumb ends). In an 80x24 window the menu fits and there is no scrollbar, which is why the 2,205-combination matrix at 80x24 and 132x43 never saw it. Screenshot: [f2-ascii-menu-scrollbar-80x14.png](m35-screens/f2-ascii-menu-scrollbar-80x14.png); data: [ascii-tier-small-windows.json](m35-screens/data/ascii-tier-small-windows.json).

Expected: `#` and `|`, ASCII only. The people who pick the ASCII tier are the ones whose terminals cannot draw those characters. Fix: FIX-M35-2, with a test that draws every layout in the ASCII tier at every height from 8 to 24 and scans the cells.

### M3. The intro does not adapt to a slow link, and a key does not help (Medium)

Default motion is on, and the intro is sent in full whatever the link can carry (86 KB at 80x24, 145 KB at 132x43, about 25 KB at 16 colours). The slow-send guard (250 ms per write) never fired in my runs, because the SSH channel window and the socket buffers accept the whole intro at once, so the writes never block. When a key then ends the effect, the frames already written have to drain first.

Reproduce: `tools/slowproxy.py LISTEN TARGET 7000` (server-to-client bytes per second), `ssh -p LISTEN founder@127.0.0.1`, wait for the login box, press a key: **18.2 s** to the menu at 80x24 and **25.8 s** at 132x43 (56 kbit); with the key at 0.5 s, 6.1 s against 1.8 s with motion off. At 9.6 kbit the login box takes 8.0 s (80x24) and 18.6 s (132x43) and the menu does not appear within 60 s. [data/slow-link-1.json](m35-screens/data/slow-link-1.json), [slow-link-2.json](m35-screens/data/slow-link-2.json).

Expected: a motion-on session on a link that cannot carry the effect should drop to the static screen (no motion) or the effect should be bounded by what has been acknowledged, so that a key (or a slow link) costs about the static screen's 2 KB. A member can turn motion off only after signing in, which on these links is what takes 18 s. Limits of this measurement: a userspace proxy, not `tc`; real kernels may hold less. The finding is that nothing in the server noticed. Fix: FIX-M35-3 (for example measure unacknowledged bytes or write latency per frame, stop the effect and send the static screen when a budget is exceeded, and add a byte cap per intro).
