# QA report: M1 SSH server and waiting room

Reviewer: QA session (did not write the code; no code changed, only this file added). Date: 2026-11-02.

## Verdict

**M1 does not pass the gate yet.** Four of the five "Done when" lines are met and everything I tried against the threat model's confidentiality rules held: an unknown key learns nothing, `claim` is not an oracle, lockdown is complete, TLS cannot be downgraded, no secret reaches a log. Two things block the gate:

1. **The published container image does not exist** (H2). No tag, no release, GHCR answers `denied`. `docs/deploy.md`'s first command fails. The same image built locally does everything from an empty volume, so this is an owner action (cut a `v*` tag) followed by a re-check, not a code defect.
2. **An anonymous client can burn CPU and memory with cheap input** (H1). One connection that spams window-change requests or keystrokes pins one or more cores; four connections starve a 4-core host (probe login took 5 s against 0.01 s idle). A client that stops reading makes the server queue output without a bound. The existing flood limits only protect connection setup.

Findings: 0 critical, **2 high**, 3 medium, 8 low (plus informational notes). Fix slices for the two high findings are at the end.

## Findings

### H1. HIGH: any client can exhaust CPU and memory with window-change requests or keystrokes

- Reproduction (release musl binary, 4-core host, default limits, unknown key):
  - `storm1.py 1 10`: one session sends 35,940 `window-change` requests; server CPU **13.2 s** over 14 s wall (a debug build took 33 s for the same traffic). `storm1.py 4 10`: 4 sessions, 144,043 resizes, **96.9 s CPU in 29 s**; a probe login during the flood took **5.03 s** (0.01 s idle) and still 2.3 s afterwards.
  - 230 sessions x 300 resizes (debug build): RSS 78 MB -> 265 MB, and a fresh login timed out for over 15 s (`authentication timed out; disconnecting` in the log).
  - 10 MB of `A` sent as keystrokes into the request form (`paramiko`, one session): 22.9 s wall, **83.5 s of server CPU**, i.e. more than three cores for one connection.
  - A client that never reads: paramiko transport with `window_size=2048`, 35,914 resizes, no `recv`: server RSS **354 -> 447 MB** (+93 MB, about 2.6 KB per request) and not released after disconnect. At that rate a few million requests exhaust a small container.
- Cause: every `window-change` rebuilds the terminal and fully redraws (`Screen::resize` -> `rebuild`, `crates/server/src/ssh/screen.rs:213-224`, `draw` at `:242`); every `data` packet parses keys and redraws (`crates/server/src/ssh/handler.rs:510-535`; resize handler `:489-507`). There is no per-session rate limit, coalescing or debounce, and `session.data()` output is queued without a bound when the peer does not read. The flood limits in D22/D37 cover connection setup, authentication and form submissions, not what an authenticated-but-unknown session sends afterwards. An unknown key is accepted by design, so no credential is needed.
- Impact: the threat model's top adversary ("unauthenticated stranger ... flood the waiting room") can deny service to the sysop and members with a handful of sockets from one address. `docs/threat-model.md` "Flood limits" says the limits were tested with a real client; the post-auth channel traffic path was not covered. Memory is also not given back (musl allocator; see L10), so a flood has lasting cost.
- Verified bounded: oversized forms (24-char cap, RSS flat), the 500x200 size clamp, connection cap, fds after disconnects.

### H2. HIGH (gate blocker, owner action): the published container image does not exist

- Reproduction: `docker pull ghcr.io/pdxgeek/russh-bbs:latest` -> `error from registry: denied`; `curl https://ghcr.io/v2/pdxgeek/russh-bbs/tags/list` -> HTTP 401; GitHub MCP `list_tags` and `list_releases` for `pdxgeek/russh-bbs` -> `[]`. `.github/workflows/publish-image.yml` runs on `v*` tags only and has never run (the PR #20 body says so).

- Also unverified: the arm64 image, and the `container-build.yml` smoke job on GitHub (PR #20 says the same).

### M1. MEDIUM: the image's baked `RUSSH_BBS_DB` makes Postgres unusable in the container

- Reproduction: `docker run -e RUSSH_BBS_DATASOURCE_KIND=postgres -e RUSSH_BBS_DATASOURCE_URL=... russh-bbs:qa` (and with `-e RUSSH_BBS_DB=`): `invalid value for datasource.path from environment variable RUSSH_BBS_DB: is only used when datasource.kind = "sqlite"`; exit 1. An environment variable baked into an image cannot be unset by `docker run`, and an empty value still counts as set.
- With `RUSSH_BBS_DB` removed from the `ENV` line in a throwaway copy of the final stage, the same container started against the TLS Postgres in both `require` and `verify-full` (with `tls_root_cert=/data/ca.crt` on the volume), password absent from the log. So the `scratch`/rustls path works; only the baked variable stops it.
- Files: `Dockerfile:29`. `docs/config.md` (`tls_root_cert` row) and PR #22/D44 tell operators how to use `verify-*` in the container, which cannot be followed today. `docs/deploy.md` lists Postgres under "Not covered here", so the docs do not promise it, but the combination is the one the Postgres work targets.
- Direction: do not set `RUSSH_BBS_DB` in the image (the default `/data/config.toml` or a path default would do), or make the config accept it when the kind is Postgres.

### Low findings

- **L1. One source IP locks out everyone behind it, including the sysop and the founder claim.** After 10 connections in 20 s from one address, the founder key from the same address is reset (`kex_exchange_identification: Connection reset by peer`) while the limiter is empty. Documented as "shared NAT addresses share an allowance" (threat model), so it is a known trade-off; noted because a flood also blocks the first-run claim. Files: `AcceptLoop::admit`.
- **L2. A stray `RUSSH_BBS_*` variable stops boot.** Any variable with the prefix that no setting reads is a boot error (`crates/server/src/config/error.rs:69`). This catches typos by design, but container platforms that inject service links (Kubernetes names them `<SERVICE>_PORT`, `<SERVICE>_SERVICE_HOST`, so a service called `russh-bbs` yields `RUSSH_BBS_PORT=...`) would break boot. Mention in `docs/deploy.md` or ignore a documented allow-list of foreign names; `enableServiceLinks: false` is the workaround. Reproduced with `RUSSH_BBS_TEST_POSTGRES_ROOT_CERT` set in the shell.
- **L3. The setup token stays in `docker logs` after the claim** (and in any log shipper that saw it). It is void after the claim, so the only cost is confusion; documented in `docs/deploy.md`. The banner says "(shown once; not logged)" while `docker logs` retains it; word it as "not written through the logger".
- **L4. `docs/deploy.md` quick start and the `compose.yaml` rely on an unpublished image** (H2), and the `docker build` path needs unproxied access to rust-lang.org; behind a TLS-intercepting proxy it fails as shown. Say so, or document the host-musl alternative used here.
- **L5. `icu_properties = "2.4.0"` is declared inline in `crates/core/Cargo.toml:17`**, not in `[workspace.dependencies]` with a justification comment as every other dependency is. The PR #23 body justifies it (already in the tree via sqlx/idna, Unicode-3.0). The tokio features `signal` and `fs` were added in M1-A without being named in PR #4 ("tokio: async runtime"); harmless.
- **L6. A long banner or rules text is only clipped.** A 5000-character sysop banner fills the window and pushes menu entries off screen (the menu items after `[i]` were not visible at 80x24). Sysop-controlled, so it is not an attack, but there is no length cap and no scrolling (documented as not implemented).
- **L7. A stored width/height override that does not fit the terminal garbles the layout until cleared** (PR #21 states it). Reproducible; recoverable blind with `s w Enter h Enter`.
- **L8. "Pause" is stored and toggled but changes no output** (documented in features and in the screen: "no screen pages yet"). Listed so it is not mistaken for a feature.
- **L9. `verify-ca` also checks the host name** (rustls), i.e. behaves like `verify-full`. Safe (stricter than documented) but `docs/config.md` describes `verify-ca` as distinct; either document it or accept the difference.
- **L10. Memory is not returned after a flood.** RSS stayed at 354-455 MB after the storms (baseline 22 MB). The release image uses the musl allocator, which fragments under this churn; worth a note in the H1 slice (consider measuring a different allocator).

## Proposed fix slices

### FIX-M1-1: bound what one session can make the server do (H1, M2)

- Owns: `crates/server/src/ssh/` (`handler.rs`, `screen.rs`, `limits.rs`, `server.rs`), `docs/threat-model.md` ("Flood limits" row), `docs/decisions.md` (new decision), `docs/config.md` and `config.example.toml` if a limit becomes a key, `docs/features.md` row for rate limits.
- Acceptance:
  1. Window-change requests are coalesced or rate limited per session (at most N redraws per second; a trailing resize still takes effect), and key input is processed in batches or limited so a redraw does not happen per byte. A recorded decision names the mechanism and the defaults.
  2. Outbound data per session is bounded: when the peer's window stays exhausted beyond a limit or a time, the session is dropped, not queued without limit. An integration test with a client that never reads shows RSS (or queued bytes) stays under a stated bound.
  3. Regression tests with a real russh client: a flood of resizes and of keystrokes from one session leaves a concurrent second login within a stated latency, and CPU time per N requests stays under a stated bound (use a count/size assertion, not wall time, if timing is flaky).
  4. Re-run of the QA scripts' numbers (36k resizes, 10 MB of keystrokes, 4 attackers) recorded in the PR for before and after; `cargo fmt`, `clippy -D warnings`, `cargo test --workspace`, `cargo deny check` pass.

### FIX-M1-2: publish the image and prove it from the registry (H2; includes M1 and L4)

- Owns: `Dockerfile`, `compose.yaml`, `.github/workflows/publish-image.yml`, `.github/workflows/container-build.yml`, `docs/deploy.md`, `docs/features.md` (container row). The tag itself is the owner's action.
- Acceptance:
  1. The owner cuts a `v*` tag (or approves a pre-release tag); the workflow publishes `ghcr.io/pdxgeek/russh-bbs:<tag>` and `latest`, public and pullable without login; the PR or the tag run shows both architectures.
  2. `docker pull ghcr.io/pdxgeek/russh-bbs:latest` followed by the first-start walk (empty volume, waiting room, `claim@`, restart keeps fingerprint and sysop, `docker stop` clean) is repeated against the pulled image and recorded; the image's `RUSSH_BBS_DB` no longer prevents `RUSSH_BBS_DATASOURCE_KIND=postgres` (M1), shown by starting the pulled image against a TLS-required Postgres in `require` and in `verify-full` with `tls_root_cert` on the volume.
  3. `docs/deploy.md` states how to build behind a TLS-intercepting proxy or points at the published image only, and no longer lists Postgres under "Not covered".

Medium and low findings (M3, L1-L10) are for the orchestrator to schedule; M3 is a docs pass that can ride with either slice. After the two slices merge, a short QA re-check should repeat the H1 numbers and the pulled-image walk.

### N1. HIGH (new): per-session cost scales with the terminal size, unbounded across sessions

- **Memory, no traffic needed.** Reproduction (musl release binary, default config except `ip_burst`/`max_connections` raised so one address can open them): `ptymem.py W H 240` opens 240 sessions as 240 different unknown keys, each sends one `pty-req` of `WxH` and `shell`, then does nothing.
  - 80x24: RSS 8 -> **68 MB** (0.25 MB a session).
  - 500x200 (the clamp, `MAX_COLS`/`MAX_ROWS` in `ssh/terminal.rs:16-18`): RSS 8 -> **2,222 MB**, 9.2 MB a session, peak 2,221 MB. The default `max_connections` is 256.
  - Real container: `docker run -m 512m --memory-swap 512m` the QA image, 120 attempted sessions at 500x200: **55 sessions opened, then the container was OOM-killed** (`OOMKilled=true`, exit 137), all sessions lost.
  - 240 sessions each resizing to 500x200 once a second: peak 2,257 MB. The memory is per session, held while the session is open, and goes back (musl: RSS 11 MB after close; the glibc build kept 257-2,646 MB after similar runs, which is L10 on a non-release build).
- **CPU.** A window change at 500x200 costs about **5.8 ms** of server CPU (41.5 CPU-s / 7,200 window changes), against 0.57 ms at 80x24, and it costs the same when the size is unchanged, because `Screen::render` rebuilds the whole terminal on every window change (`crates/server/src/ssh/screen.rs:226-244`: `rebuild_now` -> `new_terminal` with a `Viewport::Fixed` of the full window, so ratatui allocates two buffers of cols x rows cells each time). Each session may do this 20 times a second (`redraw_interval`).
  - 30 sessions x 20 window changes/s (each at a tenth of its own request budget; 600 requests/s in total) to 500x200: **3.3-3.6 of 4 cores**, probe login median 267 ms (idle 98).
  - 60 sessions: 3.5 cores, probe median 761 ms. 240 sessions: 3.0-3.1 cores, probe median 1.4-1.8 s, max **4.6 s**.
  - The same 240 sessions at 80x24: 2.5 cores, probe median 129 ms, peak RSS 72 MB. So the window size is a roughly ten-fold multiplier on both axes, and an attacker picks it.
- Why it is high: this is the same class and impact as H1 (an anonymous client degrades or kills the service; an unknown key is accepted by design, so no credential is needed) and it is reached with default settings. It is milder than H1 in one respect (it needs tens to hundreds of connections, which the per-address limit admits at about 30 a minute from one address, and far faster from several addresses) and worse in another (memory, not just CPU: an OOM kill takes every member's session down and, in a container with a memory limit, restarts the process).
- Why FIX-M1-1 does not cover it: D49 (7) says the sum over many sessions is "not covered" and relies on the connection cap and the per-network limit. That is honest, but it does not say that one session's cost depends on a client-chosen number, and `docs/threat-model.md` "Flood limits" is marked "Implemented and tested" without it. The original QA report listed the 500x200 clamp as "verified bounded" and did not measure memory at that size; that was a miss in the first pass, not something FIX-M1-1 introduced. I did not build the pre-fix commit, so I have not shown that `5dd4fdd` behaves the same, but the viewport code is unchanged in kind.
- Direction (for the fix slice, not applied here): size the terminal to what the screens use rather than to the window (the screens are 80-column layouts; a fixed viewport of, say, 120x50 centered in a larger window needs no more memory however big the window is), or lower the clamp, and in either case stop rebuilding for an unchanged size; and put a cap on total render cells (or on memory) across sessions so that 256 sessions cannot exceed a stated bound.

### N2. LOW (new): the `docs/deploy.md` recipe for putting a CA on a fresh volume leaves `/data` unusable

- Reproduction: `docker volume create v`; run the documented `docker run --rm -v v:/data -v "$PWD:/in:ro" alpine sh -c 'cp /in/ca.crt /data/ca.crt && chown 65532:65532 /data/ca.crt'`; start the image with the Postgres variables: `Error: host key file /data/host_ed25519_key: Permission denied (os error 13)`, exit 1 (shown with `require` and `verify-full`). A fresh volume gets its contents from the **first** image that mounts it; `alpine` has no `/data`, so Docker creates it `root:root 0755`, and the server (UID 65532) cannot write the host key.
- Workaround that I used and that works: initialise the volume with the server image first (`docker run --rm -v v:/data russh-bbs:... --help`), which copies the image's `/data` owned by 65532, then copy the CA. Or `chown 65532:65532 /data` in the same `sh -c`. The error text is clear, so this is a docs trap, not a security issue. Files: `docs/deploy.md` "Postgres" section (third bullet after the code block).

### FIX-M1-3: bound what one session costs, not just what it sends (N1)
