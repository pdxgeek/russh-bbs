# QA report: M3 Public core

Reviewer: QA session (did not write the code; no code changed, only this file, M3 status text in `docs/features.md`, and rows in `docs/coordination.md`). Date: 2026-11-03.
Tested: `main` at **`48494ad`** (merge of PR #69; M3-A to M3-J, FIX-M3-1 are in). Scope: M3 "Done when" in `docs/milestones.md` and the QA-gate brief.

## Verdict

**M3 passes the gate.** The three "Done when" clauses hold over real clients against the container image built from `main`, from an empty volume: three members (alice, bob, carol) posted, replied with a quote, searched, chatted (presence, a whisper) and exchanged mail over plain OpenSSH 9.6; a malicious feed (escape codes, C1, bidi, private-use, marker codepoints, SSRF redirects, bombs, oversize, slow drip) was neutralized by the tests **and** live through the running server; the layout and theme switch live. I found **no high finding**: nothing leaked to an unknown key, no hostile text reached the screen, the log or the database as a control or marker character, mail was never readable at rest, and every limit I flooded held.

Three **medium** findings and several low ones are below. As in M2, the next milestone should not start until the medium rows (FIX-M3-3 to FIX-M3-5) are Done or the owner accepts them.

## Findings

### M1. Telnet shows a new invite code in clear (Medium)

D85 (2) removed the waiting room, claim and invite redemption over telnet "because each would put a key, an invite code or a setup token on the wire". But `Invites` is still in the telnet menu, and creating an invite shows the one-time code.

Reproduce: telnet on and `allow_login` on, a member with a password signs in over `telnet`, `i`, `c`. The screen shows `Invite code: GTKP-KHC4-...` (also true of the demoted sysop, within the member quota). Anyone on the path can read and redeem it first. Expected: withhold invite creation over telnet like mail ("Invites are available over ssh."). Fix: FIX-M3-3.

### M2. Board list does not scroll (Medium)

Reproduce: as the sysop add 20 boards (feeds do this fast). The list draws 18 rows; `Down` keeps moving the cursor past the drawn rows (the highlight disappears) and `Enter` opens a board that is not on screen (`F-cookie` opened blind); `1`-`9` only reaches the first nine. The notice line "Feed added" is also pushed off the screen by a long list. No data is lost (search still finds posts), but boards past the screen are effectively unreachable and nothing says so. Fix: FIX-M3-4 (scroll or page the list; keep the notice visible). **Fixed on `fix/m3-board-list`:** the board list, the thread list and search results scroll with the cursor, a position line (`7-21 of 25`) shows when not everything fits, the notice and selected row are always drawn (the help line and the heading's extra lines give way on a very small screen), and digits count the drawn rows.

### M3. No CA store in the image, https feeds cannot load (Medium)

Start: `feeds.enabled=true` in the image. The log says `no CA certificates found: https feeds cannot be verified and will not load`. Since plain http needs a per-feed flag and is discouraged, the feed feature cannot be used in the documented container. `deploy.md` explains the missing CA store for Postgres only. Fix: FIX-M3-5 (document it and offer a way, for example a `feeds.tls_root_cert` file on the volume like Postgres, or a CA bundle in the image, an owner decision).

- `docker pull alpine:3` answered `429 Too Many Requests` on every try (about eight, over 30 minutes). ### Verdict

**The login model passes the walk with two Medium findings and no High.** Joining in all three registration modes, the founder claim, routing by ssh user name, "I already have an account", My keys, device links, staff recovery, telnet and the restart all behaved as D93 to D97 say, over real OpenSSH 9.6 and a telnet client, against the container image from the repo `Dockerfile` and an empty volume. ### Findings

**P1. A newer code does not void the older unused one (Medium).** D97 (3) and (4), `accounts.md` and the screen ("a new code voids the last unused one") say so. Reproduce, link code: sign in as a member, Members, My keys, Link a new machine twice (codes A then B); on a second machine `ssh new@host`, Link this device, type **A**: it signs in as the member. `login_code.voided_at` is `NULL` for A (and for every older code in my run); only `redeemed_at` was set. Same for staff recovery: the founder issued two codes for `erin`, the **first** redeemed with a new key and password. Impact: a code given to the wrong person, or issued by mistake, cannot be cancelled by making another; a recovery code stays usable for 24 hours. Fix: FIX-M3-13.

**P2. Removing a key or changing the password does not end live sessions (Medium).** Reproduce: session S1 signed in with key C; session S2 (key A) removes C under My keys (database: 0 rows for C, `key.removed` audited). S1 keeps working (mail, forums). Likewise `gina` has a password session S1; S2 changes her password; S1 keeps working, and the old password is refused for new sign-ins. The login notice tells the member "remove the key under My keys, change your password, and tell the sysop", so the stolen session survives the advice. The idle timeout (600 s) and the minutes-per-day limit bound it only if the thief stops being active. Fix: FIX-M3-14 (end other sessions of the account when a key is removed, when a password is set or changed, when a recovery code is redeemed; or document it as a limit and say so in the notice).

**P3. A privacy sentence remains in the UI (Low).** Waiting room, `r`: "Privacy: in this version the server can read everything except PGP-encrypted mail and files you encrypt yourself." (`core::waiting_room::strings::PRIVACY_NOTE`). D93 says people read this in the docs, not on screens; this is the one screen I found that still states it (267 screens crawled). It is not a lock or an overclaim, so Low. Fix: FIX-M3-15 (remove it, or record that the rules screen is the sysop's published policy).

**P4. A key-less applicant is told about "the key" (Low).** Approving `erin` (no key) says "Approved. The account exists and the key can sign in now."; the queue header says "Approving makes an account for the key that asked." Erin signs in by password. Fix: FIX-M3-16.

**P5. Stale Password screen text (Low).** "A password signs you in over SSH only if the sysop has turned password login on." Password login has been on by default since D96. Fix: FIX-M3-17.

**P6. The per-handle limit is a targeted lock-out (Low, design trade-off).** Anyone can keep a handle's password sign-in refused by sending one wrong password every 30 seconds from any address; I saw `carol`'s correct password refused from a second address after 8 wrong guesses. Keys are not affected, but a **password-only account** (carol, every telnet-made account) has no other way in, and the same limiter guards "I already have an account" and the code forms. Documented in `config.md` ("per handle (burst 5, then one per 30 s)"); the new thing is that password-only accounts are now first class (D94). Fix: FIX-M3-18, decided by the owner and recorded as D100: a key never locks out, the per-handle limit is a gentle backoff that one correct password clears, and the per-network limit carries the weight. Re-verified in the FIX-M3-18 PR (see its description).

**P7. Telnet link codes (Info).** A telnet member can make a link code, and add or remove keys, with the code on the clear wire. The page says the code works from ssh only. Anyone who can read the telnet session already has the password, and the password is enough to bind a key under "I already have an account", so this adds no exposure beyond D94 (4a). Recorded so the owner sees it.
