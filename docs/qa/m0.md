# QA report: M0 Foundations

Reviewer: QA session (did not write the code; no code changed). Date: 2026-11-02.
Branch under test: `m1/store` at `639bfbc` (holds all of M0 plus M1-A and M1-B; `main` does not yet contain M0-B and M0-C). This report is on `qa/m0`, PR base `m1/store`.
Scope: M0 "Done when": CI green on fmt, clippy, tests and cargo-deny; sanitizer and icon registry have tests. M1 code was not reviewed, only run as part of the workspace.

## Verdict

M0's "Done when" is **met**: every validation command passes locally, CI is green on all three M0 PRs, and the sanitizer and icon registry have tests. Two documented guarantees do not hold, however. The sanitizer neutralizes only the private-use range, so the **Unicode and ASCII tiers of every security marker can be typed by any user** (finding F1, high). The sanitizer also lets several invisible "filler" characters through (F3, medium). Per the QA gate, F1 needs a fix slice and re-check before M1 closes; the proposed slice is at the end.

Findings: 0 critical, **1 high**, 4 medium, 8 low.

## Findings

### F1. HIGH: security markers are forgeable by content in the Unicode and ASCII tiers

- Reproduction: sanitize `"x ⚠ y"`, `"x ⊛ y"`, `"x SERVER-READABLE y"`, `"x KEY-CHANGED y"` with `SingleLine`/`MultiLine`; all returned unchanged. Same for every content icon. Confirmed for all 4 markers x 2 tiers from the harness output. A username can also be exactly `KEY-CHANGED`, `E2EE` or `SIGNED` (F2).
- Impact: AGENTS.md ("content cannot spoof UI icons or security badges"), `docs/threat-model.md` Security chrome ("Content can never produce them: the sanitizer strips the private-use range"), `docs/ui.md` Implemented and the module docs in `crates/core/src/icons/mod.rs:1-32` all claim content cannot produce the markers. That is true only for the Nerd tier. A malicious member or feed item can post a fake `E2EE` / `⊛` badge, or a fake `SERVER-READABLE` absence, or a fake `KEY-CHANGED` alarm, and on the default tiers it is indistinguishable from chrome. Violates the non-negotiable honesty and "security cues" rules once a front end renders it. No front end uses the registry yet, which is why this is high and not critical.
- Files: `crates/core/src/icons/mod.rs` (`SecurityMarker::entry`, from line 163: Unicode glyphs and bare-word ASCII labels), `crates/core/src/sanitize/scan.rs:82-84` (`is_private_use`, the only class neutralized to U+FFFD), `crates/core/src/icons/tests.rs` (tests only assert the Nerd tier is replaced).
- Direction (for the fix slice to decide, recorded as a decision): give chrome a form content cannot produce. Options: render the Unicode and ASCII markers only inside a delimiter/attribute that the sanitizer removes or neutralizes everywhere in content (for example a reserved bracket form or an SGR style a renderer applies out of band), have the sanitizer neutralize the specific Unicode marker glyphs and the exact marker words and brackets in content, or require renderers to draw chrome in a reserved screen region and style. Tests must prove the chosen mechanism for all three tiers.

### F2. MEDIUM: no reserved usernames; names can equal security-marker text or staff names

- Reproduction: `sanitize_username` returned `Ok` for `admin`, `sysop`, `root`, `system`, `everyone`, `SERVER-READABLE`, `KEY-CHANGED`, `E2EE`, `SIGNED`. `rg` for a reserved-name list across `crates/` finds none, and the store only enforces skeleton uniqueness.
- Impact: a member can register as `sysop`/`admin`/`system` (if the real sysop uses another name) and impersonate staff; `KEY-CHANGED` or `SIGNED` as a username is a direct instance of F1 in a list or byline.
- Files: `crates/core/src/sanitize/username.rs:75` (`sanitize_username`); store insert `crates/store/src/sqlite.rs:99-110` (M1-B, not reviewed further).
- Note: policy belongs with F1's slice or the store owner; compare on the skeleton so `Sy50p` is also blocked.

### F3. MEDIUM: invisible filler and format characters survive the sanitizer

- Reproduction: `SingleLine::new(100).sanitize("a\u{3164}b")` returns the input unchanged. Full list in the Unicode classes table: U+3164, U+115F/1160, U+FFA0, U+2800, U+17B4/5, U+034F, U+00AD, U+180B/E, U+206A-206F, U+FFF9-FFFC, U+0600-0605/06DD/070F/08E2/110BD (prepended concatenation marks), and Unicode spaces.
- Impact: subjects, file names, one-liners and descriptions can be visually blank or made to look empty, hide text from a moderator reading the screen, or defeat "is empty" checks; Arabic number signs and interlinear annotation characters alter how neighbouring text renders. The docs promise "invisible-character removal" and list a specific set, so this is a gap rather than a misstatement, but the stated goal (content cannot hide or reorder text) is not met.
- Files: `crates/core/src/sanitize/scan.rs:93` (`is_invisible_format`).
- Note: the property test `assert_clean` (`crates/core/src/sanitize/tests.rs:239`) only checks controls, private-use and a bidi subset, so it cannot catch this class (F10).

### F4. LOW: no cap on combining marks

- Reproduction: `a` + 500 x U+0301 with limit 1000 keeps all 501 chars.
- Impact: bounded by the char limit, but one cell can carry hundreds of marks. Terminals render overlap onto adjacent lines or columns, and any width computation that uses `chars().count()` is wrong for that line.
- Files: `crates/core/src/sanitize/scan.rs:27` (`clean`).

### F5. LOW: some Unicode-tier glyphs are emoji-capable, contradicting D18

- U+26A0 (WARNING SIGN) and U+2709 (ENVELOPE) are Emoji=Yes in UTS #51. D18 says the tier "avoids ... emoji presentation". Some terminals/fonts draw them as 2-cell color emoji, breaking the 1-cell width entry. Not testable here (needs real terminals and fonts).
- Files: `crates/core/src/icons/mod.rs` (Mail and KeyChanged entries), `crates/core/src/icons/width.rs:34-52`.

### F6. LOW: Unicode `ServerReadable` marker is ambiguous

- The Unicode glyph for "the server can read this" is `⊘` (CIRCLED DIVISION SLASH), conventionally read as "none/forbidden/blocked", the opposite of the claim. The Nerd glyph (`fa-eye`) and the ASCII label are fine.
- Files: `crates/core/src/icons/mod.rs`, `ServerReadable` entry. Fold into the F1 slice.

### F7. LOW: `ContentIcon::Lock` name and its non-Nerd forms

- D18 renders `Lock` as a key and relies on text label `restricted`, which satisfies the honesty rule in spirit. But the type is still called `Lock`, so it will surface as "lock" in code and in the GraphQL icon names (`docs/ui.md` says web UIs receive names). The Unicode glyph (`⚷`, an astrological symbol) and ASCII form (`[x]`, which reads as "checked/closed") do not convey "restricted". Recommendation: rename to `Restricted` (D18 already allows this) and choose clearer fallbacks.
- Files: `crates/core/src/icons/mod.rs` (`ContentIcon::Lock`), `docs/ui.md`, `docs/decisions.md` D18.

### F8. LOW: `username_skeleton` gaps and public API

- Lookalikes that stay distinct: `vv`/`w`, `cl`/`d`, `nn`/`m`, `S5`/`ss`, `B8`/`bb`, `q`/`g`, `2`/`z`, `5`/`s` (only `rn`/`m` is documented). `username_skeleton` is also `pub` and accepts any `&str`, so a caller passing un-normalized text gets a non-ASCII skeleton.
- Files: `crates/core/src/sanitize/username.rs:106`.

### F9. LOW: silent data loss on unterminated strings; separators glue words

- An unterminated OSC/DCS swallows the rest of the input with no signal to the caller (as D16 documents). Separately, VT (U+000B), FF (U+000C), NEL (U+0085), LS and PS are deleted rather than turned into a space in `SingleLine`, so `"a\x0Bb"` becomes `"ab"`.
- Files: `crates/core/src/sanitize/scan.rs:27` (`clean`), `:160` (`skip_string`).

### F10. LOW: property tests are narrower than the claim

- `assert_clean` checks no control, no private-use, a bidi subset and no ESC. It does not check noncharacters, tag characters, `U+200B/2060/FEFF`, escape-sequence residue (e.g. a stray `31m`), or the F3 class. `any::<char>()` rarely produces the specific characters that matter. There is no `cargo-fuzz` target; M0 allows "fuzz or property tests", and the threat model lists the fuzz target as Planned, so this is not a gate failure.
- Files: `crates/core/src/sanitize/tests.rs:225-262`.

### F11. LOW: stale and slightly inaccurate status text

- `docs/features.md` "Workspace, CI, threat model" says "CI itself not yet seen running on GitHub". PRs #1-#3 show it ran and passed. Update when the row is next touched.
- PR #2 says "29 core tests"; the sanitizer has 28 tests today (23 unit + 5 property) and icons has 18. Minor.

### F12. LOW: CI actions are tag-pinned, not SHA-pinned

- `.github/workflows/ci.yml` uses `actions/checkout@v4`, `Swatinem/rust-cache@v2` and `EmbarkStudios/cargo-deny-action@v2`. Tag pins can move. Acceptable for M0; worth pinning to SHAs before the closed beta.

### Info (no action)

- Marker widths differ widely by tier (2 / 1 / 4-15 cells). `Rendered::width()` reports it correctly, but layouts must not reserve a fixed icon column for markers.
- U+FFFD survives the sanitizer, so content can produce the same character the sanitizer uses as its replacement marker. Harmless today.

## What could not be tested here

- Alignment and width of the icon glyphs in real terminals and fonts (several emulators, Mono vs non-Mono Nerd fonts, CJK locales). Needs a human or a terminal farm; F5 depends on it.

- GitHub Actions internals beyond the check-run conclusions (logs were not read).

## Proposed fix slices

Only high-or-above findings require a slice. Medium and low findings are listed above for the orchestrator to schedule.

### FIX-M0-1: make security markers unforgeable in every tier (F1; fold in F2 and F6 if convenient)

- Owns: `crates/core/src/icons/`, `crates/core/src/sanitize/` (including `username.rs`), `docs/ui.md`, `docs/threat-model.md` (Security chrome status), `docs/decisions.md` (new decision), `docs/features.md` rows for sanitizer and icons.
- Acceptance:
  1. A recorded decision names the mechanism that keeps the Unicode and ASCII forms of `SecurityMarker` unproducible from content (or restates the honest limit if the chosen mechanism is renderer-side).
  2. A property test proves, for all three tiers and all four markers, that no string passed through the sanitizer (`SingleLine`, `MultiLine`) contains the marker's glyph or label in a form a renderer would draw as chrome. Mutation check: reverting the mechanism makes the test fail.
  3. `sanitize_username` rejects the marker labels (compared on the skeleton) and a reserved-name list (`sysop`, `admin`, `root`, `system`, `everyone`, plus the labels), with tests.
  4. The `ServerReadable` Unicode glyph no longer reads as "prohibited"; a test or doc states why it is honest.
  5. Docs no longer claim more than the tests prove; `cargo fmt`, `clippy -D warnings`, `cargo test --workspace` and `cargo deny check` pass.
