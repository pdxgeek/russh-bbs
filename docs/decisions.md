Plainly: sender, recipient, time, whether it was opened and a message's size are stored unsealed in the database. That is fine for stage 1; it means someone with the database can see who wrote to whom and when, and not what. Reports (10) are clear copies by design. **Drafts: mail drafts are not stored at all (owner review, 2026-11-03).** The editor is opened for mail with no draft context, so it offers no save-draft and nothing is written to the `draft` table (an integration test counts zero rows after a refused send, and `access_paths` checks it too). *Why not seal them:* the `draft.body` column is `CHECK`-limited to 16,000 characters, and a sealed 8,000-character body is up to about 43,000 characters as text, so sealing needs a table change (a rebuild on SQLite) and a wrapper around the draft store, which is out of proportion for stage 1. *Cost:* Esc discards. A message that was refused (daily limit, full mailbox) is kept **in memory for the session only** and comes back as the starting text of the same message, until the member leaves mail or disconnects. Sealing drafts under the mail key stays a possible follow-up. **Telnet: mail is withheld by default (owner review, 2026-11-03).** The Mail menu item over telnet (D27) shows "Mail is available over ssh." and nothing is read or sent; the screen refuses to open and, as a second line of defence, the session is given no mail keys. Reversible by the owner: remove the check in `Screen::apply_keys` and `Screen::mail_keys` (`ssh/screen.rs`). # Decisions

| D37 | **Waiting room design (M1-C).** (1) The screen set is a core rule (`russh_bbs_core::waiting_room::screens`): `invite` = rules, request an invite, redeem an invite; `apply` = rules, application form; `open` = rules, create-account form. Per key at the top of `auth_publickey`, for members and strangers alike: burst **5**, then one per **10 s**; the client sees an ordinary "Permission denied". Per session: **5** form submissions (invalid ones count), then the session is closed. Each limiter remembers at most **10 000** sources; when full it first drops idle entries (equivalent to absent) and then the oldest eighth, so a flood of distinct sources cannot grow memory, at the cost of resetting some limited sources early. GCRA needs one number per key and no timer task, which makes the bounded table and the fake-clock tests simple. Dropping at accept is the cheapest possible refusal.
