# Decisions

Decided items are not reopened without the owner. Open items need the owner before work depends on them.

## Decided

| ID | Decision | Why |
|---|---|---|
| D1 | The MVP works over plain `ssh` and `sftp` with **no custom client**. | "No install required" is the MVP goal. |
| D2 | **Registration mode is a sysop setting** with three values, default `invite`. `invite`: unknown keys reach only a waiting room (request or redeem an invite). `apply`: anyone can submit a membership application that lands in the sysop queue; the account is inactive until approved. `open`: an unknown key can create an active account at once, subject to rate limits and an optional cap on new accounts. Amended by the owner on 2026-11-01; the original decision was invite-only with no option. | Quiet by default; the invite tree is still the trust graph in `invite` mode. Sysops who want a classic apply-and-approve board or an open board get it by configuration, not by a fork. |
| D3 | In the MVP **the server can read everything** except PGP-encrypted mail and files users encrypt themselves. The product states this. | Real E2EE needs code on the user's machine; faking it would be dishonest. |
| D4 | True E2EE (DMs via double ratchet, groups via MLS) comes **after the MVP** with a native client. | A server-rendered session sees keystrokes. |
| D5 | Public spaces are server-side and plaintext; member-to-member private spaces are E2EE once the client exists. No mixed or silent-fallback rooms. | Locks must mean what they say. |
| D6 | Storage sits behind traits in core. **The datasource is a sysop setting**: `sqlite` (default, WAL, single file) or `postgres` (a server URL). The Postgres backend must also work against **PGlite**, which is used as the lightweight Postgres for development and CI through its wire-protocol socket server; there is no in-process PGlite embedding in Rust, so PGlite is a deployment of the Postgres backend, not a third backend. **MySQL and MariaDB are not supported** and will not be. Amended by the owner on 2026-11-01; the original decision was SQLite only. | SQLite keeps the single-binary, single-file story; Postgres is for sysops who already run it. Two dialects is the limit the project can test honestly. |
| D7 | Stack: `russh`, `tokio`, `ratatui`/`crossterm`, `sqlx`, `serde`/`toml`, `tracing`. | Library over bespoke. |
| D8 | Credits are an **internal, non-transferable ledger**. No token, no chain, not redeemable for money. | Avoids financial-service risk. Lightning tips are a possible later optional module. |
| D9 | Mail is staged: internal first (MVP), then inbound SMTP, then outbound through a relay, then IMAP. Never run a hand-written MTA. | Deliverability and abuse cost. |
| D10 | Menu tree, layout, theme, and icon set are **separate layers**. Security cues are fixed chrome. | Themeability without spoofing risk. |
| D11 | Offline readers (QWK) are **out of scope**. | Owner decision. |
| D12 | Door games: Rust-native first-party doors first; WASM sandbox for community doors later. Remakes are original ("clean-room"), not ports of copyrighted code, unless a license permits it. | Safety and copyright. |
| D13 | The software is named **russh-bbs**. A running board has its own name. Not affiliated with the `russh` project. | Software name vs. board name. |
| D14 | Federation, directory listing, finger, and NNTP are opt-in and post-MVP. | Quiet, invite-only feel. |
| D15 | Workspace uses **edition 2024** and resolver 3, toolchain **pinned to an exact stable release** in `rust-toolchain.toml` (bumped deliberately in its own change), workspace crates `publish = false`, with no license declared. | The rust-coding skill assumes 2024 (AGENTS.md allows 2021 or later); a new repo gains nothing from an older edition. The pin exists because floating `stable` made local and CI clippy disagree (a newer lint failed only in CI); the trade-off is a manual bump. `publish = false` plus `licenses.private.ignore` in `deny.toml` lets cargo-deny pass without inventing a license (Q1 stays open). |
| D16 | Sanitizer limits count Unicode scalar values (`char`), not bytes or grapheme clusters. Escape sequences are parsed by a small hand-written scanner (ESC, CSI, OSC, DCS/SOS/PM/APC, nF and two-byte escapes, and the 8-bit C1 forms); an unterminated string sequence swallows the rest of the input, as a terminal would. Private-use and noncharacter codepoints become U+FFFD (visible, stable, not itself private-use) rather than being deleted; controls and bidi/invisible characters are deleted. Single-line context turns newline, CR and tab into a space; multi-line keeps `\n` and `\t` and normalizes CR and CRLF to `\n`. | Graphemes need a segmentation dependency and Unicode tables for no security gain; a `char` cut can at worst leave a trailing combining mark, which is harmless once controls are gone. Replacement keeps users aware that something was there. Properties (idempotence, no ESC/control/PUA/bidi in output) hold because ESC and C1 never survive. |
| D17 | Usernames are **rejected, not repaired**: NFKC, then only `[A-Za-z0-9_-]`, 2 to 24 characters, starting with a letter or digit. Confusables: non-ASCII is rejected outright, and a minimal ASCII skeleton (`username_skeleton`) is the uniqueness key. Unicode names can be added later with a real confusables table. | Strict and boring is the safe default for names that appear in security-relevant places. Adds only the `unicode-normalization` dependency. |
| D18 | Icon registry design: closed enums, not strings (`ContentIcon`, `SecurityMarker`, wrapped by `Icon`); three tiers `NerdFont`/`Unicode`/`Ascii`. Nerd Font glyphs are BMP Font Awesome codepoints (U+F0xx), not the plane-15 Material range. Width policy: Nerd glyphs **reserve 2 cells** and render with one trailing space; plain-Unicode glyphs are restricted to BMP, East Asian Width Neutral characters (1 cell); a glyph without a width entry falls back to ASCII. Security markers' ASCII glyph is their label (`SERVER-READABLE`, `E2EE`, `SIGNED`, `KEY-CHANGED`). The generic `lock` icon renders as a key / "restricted", never the padlock, which is reserved for `E2eeLock`. | A separate security type lets APIs refuse to accept chrome where only content is meant. Reserving 2 cells is safe for both Mono (1-cell) and overflowing (2-cell) fonts. Neutral-width Unicode avoids CJK-locale double-width surprises and emoji presentation. A padlock that means "restricted access" would contradict "never show a lock where the server can read it". Owner may rename `Lock` if they dislike the key. |
| D19 | **Q5 resolved: ratatui drives the PTY through a per-session in-memory backend.** Each session owns `ratatui::Terminal<CrosstermBackend<OutputBuffer>>` with a **fixed viewport** sized from `pty-req` and `window-change`. A draw writes escape sequences into the buffer; the handler drains the buffer and sends it with `Session::data`. Crossterm is used only to emit sequences (alternate screen, cursor); **input is parsed by our own small byte parser** (`ssh::terminal::parse_keys`), because crossterm's event reader reads the server's own stdin and cannot see channel bytes. No hand-rolled terminal abstraction layer. Window sizes are clamped to 500x200 and 0 means 80x24. | Prototyped in M1-A: the placeholder renders, resizes and restores the terminal on `q`, verified with OpenSSH. A fixed viewport means ratatui never asks the server's own tty for a size, so sessions cannot affect each other or the console. (Caught by CI: ratatui's `Terminal::resize` still calls `backend.size()`, which the crossterm backend answers from the server's own tty, so `Screen::resize` clears the client and builds a new fixed-viewport terminal instead.) A bespoke abstraction would re-implement diffing and widgets that ratatui already tests. Costs: output is diff-based (blank cells are skipped, so a phrase arrives split by cursor moves; tests assert on whole words), and ratatui does not expose its writer, so the buffer is shared through an `Arc<Mutex<Vec<u8>>>` taken for a copy only, never across an `.await`. Later screens that push updates on a timer will need a per-session task that owns the `Screen` and an mpsc inbox; that is M3 and not designed here. The parser is stateless between chunks, so an escape sequence split across two reads is dropped; fine for `q`, revisit when screens take real input. |
| D20 | Host key: **Ed25519**, OpenSSH private-key format, unencrypted, at a path outside the repo. Default `$XDG_DATA_HOME/russh-bbs/host_ed25519_key`, else `$HOME/.local/share/russh-bbs/host_ed25519_key`; override with `--host-key` or `RUSSH_BBS_HOST_KEY`. If neither the flag nor `HOME` is set the server refuses to start rather than guessing. Generated on first start with mode **0600** (directory 0700) using `create_new`, so racing first starts cannot overwrite a key. An existing file that is group- or world-accessible, not Ed25519, encrypted, or unparsable is a **startup error**; it is never regenerated or overwritten. The SHA-256 fingerprint is logged at startup; the private key is never logged and `HostKey` has a redacting `Debug`. | A stable fingerprint is the whole point of a published host key (threat model, Transport). Refusing loose permissions follows OpenSSH. Failing instead of regenerating prevents silently changing the identity users have pinned. An encrypted key would need a passphrase prompt at boot; not worth it for a daemon. Rotation is a manual operator action (replace the file) and clients will see the standard changed-host-key warning. |
| D21 | Crypto backend and key types: `russh` with **`ring`** and without the default `aws-lc-rs` and `rsa` features. Clients can authenticate with **Ed25519 or ECDSA** keys; **RSA client keys are not supported**. Server banner is `SSH-2.0-russh-bbs` (no version). | `rsa` pulls the `rsa` crate, which has an unfixed timing side-channel advisory (RUSTSEC-2023-0071, `patched = []`, checked in the advisory DB), and `cargo deny` fails on advisories; `aws-lc-rs` needs a C build and pulls `aws-lc-sys`, whose licenses I did not check against `deny.toml`; `ring` passed `cargo deny` with no change to the allow list. Ed25519 is the default `ssh-keygen` type on current OpenSSH, so the cost is users with only an old RSA key, who must generate an Ed25519 key. Owner can reverse this if RSA users matter more than the advisory. |
| D22 | Transport limits live in one `ssh::Limits` struct with defaults: **30 s** from TCP accept to authenticated (enforced by our own accept loop, since russh has no pre-auth deadline), **6** auth attempts, **1 s** delay on a failed auth (instant for the OpenSSH `none` probe), **600 s** idle timeout, 30 s keepalives (3 missed = drop), **256** concurrent connections (excess dropped at accept), at most **4** session channels per connection and one PTY/shell. Per-IP and per-key rate limits are M1-C and plug in at `AcceptLoop::admit` and `ClientHandler::auth_publickey`. | Bounds what an unauthenticated stranger can hold. Numbers are guesses to tune from real use, exposed as flags/env where useful (`--auth-timeout-secs`, `--idle-timeout-secs`, `--max-connections`). |
| D24 | Datasource design: one `Store` trait family in core, one backend module per database in `crates/store` (`sqlite`, `postgres`), each with its own forward-only migration set, since the dialects differ (FTS5 vs `tsvector`, `INTEGER PRIMARY KEY` vs `BIGSERIAL`). Shared behavior tests run against every backend. A feature is not marked Implemented until it passes on both. No `AnyPool` or dialect-neutral SQL that is only tested on one. | Dialect-neutral SQL hides bugs until the other backend is used in production. |
| D25 | The server ships as a **container image** as a first-class deliverable from M1: static musl build, non-root, unprivileged listen port (default 2222), all state under one volume (`/data`: SQLite file, host key, blobs), config from TOML plus environment overrides, logs to stdout, SIGTERM shutdown that checkpoints SQLite. The container is not the door sandbox (that rule holds inside the process). Decided by the owner on 2026-11-01. | Reproducible runs for members, sysops, and reviewers; the single binary makes this cheap. |
| D27 | **Telnet is an optional transport, disabled by default.** `telnet.enabled = false` ships; when a sysop turns it on, unknown connections get the same waiting room as SSH, and member login over telnet requires a second opt-in `telnet.allow_login` plus a per-member password (argon2id hash, set only over SSH, never required for SSH). Every telnet screen carries a fixed `UNENCRYPTED` security marker that layouts and themes cannot hide (D10), and the banner says the session can be read on the wire. SFTP, invite redemption, and sysop functions are SSH-only. Telnet is an M3 slice; it must not change the SSH server. Decided by the owner on 2026-11-01. | Classic BBS reach for sysops who want it, without weakening the default. The marker and the separate password keep the honesty rule and keep SSH keys out of the clear. |
| D23 | The waiting room is built around the registration mode from the start (M1-C), and the `apply` and `open` flows ship in M2 with the sysop queue. The waiting room reveals nothing about members, boards, or stats in any mode; `apply` and `open` only add a registration path. | Avoids retrofitting the waiting room; the honesty and no-leak rules do not depend on mode. |
| D24 | **Q4 resolved: `sqlx` (SQLite only, compile-time checked `query!`/`query_as!`)**, with the offline query data committed in `crates/store/.sqlx/` and `SQLX_OFFLINE=true` set in CI, so no build or test needs a live database. The workspace dependency is `default-features = false` with `runtime-tokio`, `sqlite`, `macros`, `migrate`: the default features add the MySQL and Postgres drivers, and `sqlx-mysql` pulls the `rsa` crate (RUSTSEC-2023-0071, see D21). With SQLite only, `cargo deny check` passes with no change to `deny.toml`. Regenerate the data after changing a query: create a scratch DB from `crates/store/migrations/`, then `DATABASE_URL=sqlite://<scratch> SQLX_OFFLINE_DIR=$PWD/crates/store/.sqlx cargo check -p russh-bbs-store` (or `cargo sqlx prepare`). A query with no matching data fails to compile offline, which is the stale-data check. | Matches D7 and the rust-coding skill: row types come from the schema, a typo in SQL fails the build. Costs: a larger dependency tree than `rusqlite` (async pool, macros), and a manual regenerate step on query changes. `rusqlite` would have needed a blocking-thread wrapper around every call. |
| D25 | Store design: **WAL**, `synchronous=NORMAL`, foreign keys on (set per connection), 5 s busy timeout, pool of **5**. Ids are `i64` `AUTOINCREMENT` rowids wrapped in newtypes (`AccountId`) in core, minted only when a row is mapped. Timestamps are **integer Unix seconds** set by the database (`unixepoch()`), exposed as `UnixSeconds`. Enums (`Role`, `AccountState`, `RegistrationMode`) are stored as lowercase text with `CHECK` constraints and parsed in one place; an unknown stored value is `StoreError::Corrupt`, never a default. Usernames are unique on their confusables skeleton (D17). One key belongs to at most one account (fingerprint is the primary key of `account_keys`). The `registration_mode` setting is seeded to `invite` by the first migration and reads as `invite` if absent; an unrecognised value is an error, not a looser mode. **Only an `active` account is a member** (`MemberDirectory`); pending, approved and suspended keys are `Restricted`. The database file is created mode 0600 and a new data directory 0700. | Autoincrement ids are never reused, so a deleted account's id cannot be inherited. Seconds are enough for a BBS and avoid a time crate in M1. Text enums stay readable in a backup and a `CHECK` stops a bad writer. Fail-closed on corrupt data matches the "no silent fallback" rule. |
| D26 | **Migrations** are numbered SQL files in `crates/store/migrations/`, embedded with `sqlx::migrate!` and applied by `SqliteStore::open` at start-up. They are forward-only (no down scripts). sqlx records a SHA-384 checksum per applied migration and refuses to start if an applied file was edited (`VersionMismatch`) or if the database holds a version this binary does not know. The unit test `landed_migrations_are_unchanged` also pins the checksum of every landed migration, so an edit fails CI before it can reach a database. **Adding a migration means adding its checksum to that test; changing an existing line is forbidden.** `.gitattributes` forces LF on `*.sql` so a checkout cannot change the hash. | Implements the AGENTS.md rule "do not edit a migration that has landed" as a test, not a convention. |
